관리자 페이지 개발 · 합성 데모 검수 노트

관리자 페이지 개발, 요청 찾기·상태 변경·이력은 어떻게 검수할까요?

요청 관리 데모에서 직접 따라 하는 관리자 페이지 검수 순서입니다. 검색·상태 필터·처리 이력의 기대 결과와 실제 서버에서 별도로 확인할 저장·권한 조건을 나눕니다.

기능 이름 대신 행동과 기대 결과로 정합니다

관리자 페이지 개발을 맡길 때 ‘검색과 상태 변경이 필요해요’만으로는 검수 기준이 모호합니다. 어떤 요청을 찾는지, 상태 필터와 함께 쓸 때 무엇이 남아야 하는지, 처리 후 어떤 기록을 확인할지를 행동과 기대 결과로 적으면 개발 범위를 맞추기 쉽습니다.

아래는 이 사이트에서 직접 구현한 요청 관리 화면의 합성 시나리오입니다. 고객 납품 사례나 실제 사용자 반응이 아닙니다. 하단의 ‘데모 사용해 보기’로 이동하고, 실제 이름·연락처·고객 자료 대신 여기 적힌 예시만 사용하세요. 실제 프로젝트 문의는 별도 문의폼으로만 접수합니다.

1. 샘플 초기화 뒤 찾기와 상태를 함께 확인합니다

‘샘플 초기화’를 누르면 전체 요청은 2건입니다. ‘요청 찾기’에 예약을 넣고 처리 상태를 ‘전체 요청’으로 두면 샘플 고객 B의 요청 #2만 남아 현재 보기 1건이 됩니다. 처리 상태를 ‘검토 중’으로 바꾸면 현재 보기 0건과 조건에 맞는 요청이 없다는 안내가 나와야 합니다. #2의 시작 상태가 ‘신규’이기 때문입니다.

이때 ‘찾기 지우기’를 누르면 찾기어만 비워지고 ‘검토 중’ 상태는 유지됩니다. 따라서 샘플 고객 A의 요청 #1이 표시되고 포커스는 찾기칸으로 돌아갑니다. 목록에서 사라진 요청이 삭제된 것이 아니라 현재 보기 조건에서 제외된 것인지 구분하는 검수입니다.

2. 정확한 번호와 여러 단어의 뜻을 확인합니다

처리 상태를 ‘전체 요청’으로 바꾸고 #2를 입력하면 요청 #2만 나옵니다. #02로 바꾸면 결과가 없습니다. 이 데모는 앞자리 0을 고쳐서 다른 식별자로 취급하지 않습니다. 예약 MVP처럼 공백으로 나눈 단어는 모두 포함해야 하며, .* 같은 기호를 정규식으로 실행하지 않습니다.

이 규칙이 모든 관리자 화면의 정답은 아닙니다. 실제 개발에서는 정확한 번호 조회와 일반 단어 찾기를 구분할지, 찾을 대상이 이름·내용 중 어디까지인지, 정렬·페이지 이동 뒤에도 같은 조건을 유지할지를 업무에 맞춰 합의합니다. 이 데모에는 페이지 분할이나 대량 데이터 성능 검증이 없습니다.

3. 새 요청과 두 번의 상태 변경을 확인합니다

예시 활동명에 ‘검수 샘플’, 만들고 싶은 기능에 ‘데모 예약 신청 내역을 확인하는 관리 화면이 필요합니다.’를 입력하고 ‘데모 요청 등록’을 누릅니다. 초기화 이후라면 새 번호는 #3이고 전체 3건이 됩니다. 새 요청이 보이도록 찾기어와 상태 조건이 초기화되며, 펼쳐진 처리 이력에는 ‘요청 등록: 신규’가 1건 있어야 합니다.

요청 #3의 ‘검토 시작’을 누르면 ‘신규 → 검토 중’이 추가돼 이력은 2건입니다. 이어 ‘완료 처리’를 누르면 ‘검토 중 → 처리 완료’가 추가돼 3건이 되고, 해당 요청의 상태 변경 버튼은 사라집니다. 샘플 요청의 ‘합성 샘플 시작 상태’는 실제 등록·처리 행동과 구분해 표시합니다.

4. 보기 조건 변경과 초기화를 구분합니다

완료된 #3을 ‘처리 완료’ 상태와 #3 찾기어로 다시 찾고 처리 이력을 펼칩니다. 등록부터 완료까지 3건이 그대로 있어야 합니다. 찾기나 필터 조작은 요청 내용과 이력을 고치지 않습니다.

반면 ‘샘플 초기화’ 또는 새로고침은 입력한 #3과 이력을 지우고 합성 2건으로 돌아갑니다. 브라우저 메모리에서만 실행하며 요청·찾기어·처리 이력을 서버나 브라우저 저장소에 저장하지 않습니다. 이 데모의 최대 50개 제한은 서비스의 처리 용량이나 성능 보증이 아닙니다.

운영 서비스 검수에는 별도의 저장·권한 증거가 필요합니다

이 화면의 이력은 현재 브라우저에서 일어난 동작 순서입니다. 실제 운영자 신원, 서버 시각, 여러 기기의 같은 데이터, 수정할 수 없는 감사 로그를 증명하지 않습니다. 로그인 화면과 이력 목록이 보인다는 이유만으로 접근 통제나 기록의 무결성을 확인했다고 볼 수 없습니다.

실제 프로젝트에서는 허용된 역할만 조회·변경하는지, 저장 실패가 성공으로 표시되지 않는지, 다른 운영자의 동시 수정과 중복 요청을 어떻게 처리하는지 별도 시나리오를 합의합니다. 새로고침·재접속 후 데이터 보존, 변경 주체·서버 시각·보관 정책도 서버 구현과 배포 환경에서 검증해야 합니다. 이 데모에서는 해당 검증을 수행하지 않았습니다.

개발 범위 상담에는 이 세 가지를 알려주세요

관리할 대상 한 가지, 상태가 바뀌는 순서, 누가 조회·변경할 수 있어야 하는지를 알려주세요. 예를 들면 ‘상담 신청 / 신규→검토→완료 / 담당자만 변경’처럼 시작할 수 있습니다. 지금 사용하는 도구와 원하는 시점도 설명하면 검수 범위를 정하는 데 도움이 됩니다.

첫 문의에는 고객 목록·실제 신청 내용·계정 비밀번호를 넣지 마세요. 데모와 달라야 할 행동과 기대 결과를 먼저 적고, 서버 저장·역할 권한·외부 연동·배포가 필요한 부분은 별도 범위로 협의합니다.

예시를 따라 확인한 뒤 필요한 관리 흐름을 문의할 수 있습니다. 아래 데모는 브라우저 프로토타입이며 실제 서비스 접수·운영 기능과 구분합니다.
